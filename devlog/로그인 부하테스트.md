# 🚀 게스트 로그인 API 부하 테스트 및 성능 개선 기록

## 1. 테스트 개요

### 테스트 대상

- **API:** `POST /api/v1/auth/guest`
- **테스트 도구:** k6 + JUH APM
- **테스트 환경:** Docker 기반 환경
- **부하 조건:** 최대 50 VU, 45초 Ramp-up/Sustain
- **테스트 목적:** 로그인 API의 병목 지점을 파악하고, DB 커넥션 점유 시간과 SQL 호출 수를 줄여 성능을 개선한다.

Google 및 Apple 소셜 로그인은 외부 인증 과정에서 발생하는 제약을 고려해, 유사한 사용자 생성 로직을 가진 게스트 로그인을 테스트 대상으로 선정했다.

## 2. 1차 vs 2차 테스트 핵심 지표 비교

| 지표 (Metric) | 1차 테스트 (개선 전) | 2차 테스트 (개선 후) | 변화 |
|---|---:|---:|---|
| 요청 성공률 | 97.49% (4,510건) | 99.88% (4,140건) | **+2.39%p** |
| 요청 실패 건수 | 116건 (2.50%) | 5건 (0.12%) | **95.7% 감소** |
| P99 응답 시간 | 550ms | 290ms | **47.3% 단축** |
| 요청당 SQL 쿼리 수 | 10회 | 7회 | **30% 감소** |
| 총 SQL 쿼리 수 | 45,448회 | 28,990회 | **36.2% 감소** |
| SQL 최대 실행 시간 | 756ms | 100ms | **86.8% 단축** |

### INSERT 쿼리의 지연 시간 개선

특히 사용자 정보를 저장하는 `INSERT` 쿼리에서 큰 개선이 관측됐다.

| 지표 | 1차 테스트 | 2차 테스트 | 변화 |
|---|---:|---:|---:|
| P95 | 11ms | 2ms | 약 81.8% 단축 |
| P99 | 67ms | 6ms | 약 91.0% 단축 |

사용자 생성 과정의 지연 시간이 크게 줄어들면서 DB 작업이 집중되는 구간의 부담도 감소했다.

> **핵심 결과:** 요청 실패 건수, SQL 호출량, SQL 최대 실행 시간, P99 응답 시간에서 개선이 확인됐다. 다만 P50과 P95는 오히려 증가했기 때문에 모든 응답 구간의 성능이 개선됐다고 단정할 수는 없다.

## 3. 1차 부하 테스트 문제 관측 및 원인 분석

### 3.1. 닉네임 UNIQUE 제약조건 위반으로 인한 요청 실패

1차 테스트에서는 총 116건의 요청이 HTTP 500 오류로 실패했다.

원인은 `users` 테이블의 `nickname` 컬럼에 설정된 `UNIQUE` 제약조건 위반이었다. 동시 요청이 발생하는 상황에서 닉네임 중복이 발생했고, DB INSERT 과정에서 예외가 발생하며 트랜잭션이 롤백됐다.

#### Before — 문제 코드

```java
private String generateRandomNickname(String prefix) {
    long timestamp = System.currentTimeMillis();

    // 10초 주기로 반복되는 시간 조각
    String timePart = String.format(
        "%04d",
        timestamp % 10000
    );

    // 10~99 범위의 90가지 난수
    int randomPart = (int) (Math.random() * 90) + 10;

    return prefix + timePart + randomPart;
}
```

#### 문제점

- 시간 조각이 반복되므로 같은 닉네임 조합이 다시 생성될 수 있다.
- 난수의 경우의 수가 90가지로 제한된다.
- 동시 요청이 집중될수록 닉네임 충돌 가능성이 커진다.
- DB의 `UNIQUE` 제약조건에 의해 INSERT가 실패하고 요청 전체가 롤백될 수 있다.

#### After — 개선 코드

```java
public class NicknameGenerator {

    private static final String[] KO_ADJECTIVES = {
        "따뜻한", "고요한", "맑은", ...
    };

    private static final String[] KO_NOUNS = {
        "캔버스", "여행자", "구름", ...
    };

    public static String generate(String language) {
        String[] adjs =
            "en".equalsIgnoreCase(language)
                ? EN_ADJECTIVES
                : KO_ADJECTIVES;

        String[] nouns =
            "en".equalsIgnoreCase(language)
                ? EN_NOUNS
                : KO_NOUNS;

        int adjIdx = ThreadLocalRandom.current()
            .nextInt(adjs.length);

        int nounIdx = ThreadLocalRandom.current()
            .nextInt(nouns.length);

        int randomCode = ThreadLocalRandom.current()
            .nextInt(1000, 10000);

        return adjs[adjIdx] + nouns[nounIdx] + randomCode;
    }
}
```

#### 개선 효과

**① 닉네임 조합의 경우의 수 확장**

형용사, 명사, 4자리 숫자를 조합해 충돌 가능성을 낮췄다. 실제 충돌 확률은 배열의 크기와 조합 방식, 요청 분포에 따라 달라지며, `UNIQUE` 제약조건은 최종적인 데이터 무결성 보호 장치로 유지한다.

**② 멀티스레드 환경에 적합한 난수 생성**

`ThreadLocalRandom`을 사용해 스레드 간 공유 난수 생성기에서 발생할 수 있는 경합을 줄이고, 동시 요청 상황에 더 적합한 난수 생성을 적용했다.

**③ UX 개선**

`guest123456`과 같은 기계적인 문자열 대신 심리 분석 서비스의 분위기에 어울리는 감성적인 닉네임을 제공한다.

### 3.2. HikariCP 커넥션 풀 포화

1차 테스트에서는 특정 시간대에 HikariCP 커넥션 풀이 포화되는 현상이 관측됐다.

#### 관측 지표

| 지표 | 관측값 |
|---|---:|
| Active Connections | 20 |
| Idle Connections | 0 |
| Pending Threads | 14 |
| 특정 시점의 P95 응답 시간 | 1,144ms |
| 최악의 사례 중 하나에서 커넥션 점유 시간 | 약 690ms |

커넥션 풀의 최대 크기가 20개인 상황에서 Active Connections가 20개에 도달하고 Idle Connections가 0이 됐다. 동시에 커넥션을 획득하지 못한 요청들이 대기열에 쌓였다.

#### 근본 원인

게스트 로그인 한 번의 처리 과정에 여러 DB 작업이 단일 트랜잭션으로 묶여 있었다.

1. 사용자 생성
2. 부속 엔티티 3개 생성
3. 기본 카드 아이템 조회 및 지급
4. 가입 축하 우편 생성
5. 리프레시 토큰 조회 및 저장

이 과정에서 한 요청이 약 10회의 SQL 쿼리를 수행했고, 부가적인 작업까지 완료될 때까지 트랜잭션이 유지됐다.

문제는 단순히 SQL 쿼리 수가 많다는 점만이 아니었다. **불필요한 작업이 트랜잭션 내부에 포함되면서 DB 커넥션 점유 시간이 길어졌다는 점**이 핵심이었다.

최대 50 VU가 요청을 보내는 상황에서 커넥션 20개가 오랫동안 점유되자, 뒤에 도착한 요청들이 커넥션을 기다리면서 응답 시간이 급격히 증가했다.

---

### 3.3. 불필요한 중복 DB 조회

신규 사용자 여부를 확인하는 과정에서 동일한 조회 쿼리가 두 번 실행되는 문제도 확인했다.

#### Before — 문제 코드

```java
boolean isNewGuest =
    userRepository
        .findByAuthProviderAndProviderId(
            AuthProvider.GUEST,
            request.getDeviceId()
        )
        .isEmpty();

User guestUser =
    userRepository
        .findByAuthProviderAndProviderId(
            AuthProvider.GUEST,
            request.getDeviceId()
        )
        .orElseGet(() -> ...);
```

신규 사용자 여부를 확인하기 위해 한 번 조회한 후, 실제 사용자 객체를 가져오기 위해 같은 조건으로 다시 조회하고 있었다.

#### 문제점

- 동일한 조건의 SQL이 두 번 실행된다.
- 불필요한 DB 왕복이 발생한다.
- 요청량이 증가할수록 누적 DB 부하가 커진다.

이 문제는 첫 번째 조회의 결과를 재사용하는 방식으로 개선할 수 있다.

## 4. 코드 리팩토링 및 성능 개선 작업

### 작업 ① 닉네임 생성 로직 개선

**목표:** 동시 요청 시 닉네임 충돌로 발생하는 인증 실패 방지

시간 조각과 제한적인 난수 조합에 의존하던 기존 방식에서, 형용사·명사·4자리 숫자를 조합하는 방식으로 변경했다.

이를 통해 닉네임 조합의 경우의 수를 확장하고, 사용자에게 서비스의 분위기에 맞는 닉네임을 제공하도록 개선했다.

---

### 작업 ② 비핵심 부가 로직의 비동기 이벤트 분리 (Decoupling)

**목표:** 로그인 핵심 로직과 부가적인 가입 후처리를 분리해 트랜잭션 점유 시간 단축

#### Before — 문제 코드

```java
@Transactional
public Result<AuthResponse> loginAsGuest(
        GuestLoginRequest request) {

    User savedUser = userRepository.save(guestUser);

    // 핵심 인증과 무관한 작업까지 단일 트랜잭션에서 처리
    createSubEntities(savedUser);

    assignDefaultCardItems(savedUser.getId());
    sendGuestWelcomeMessage(savedUser.getId());

    return generateAndStoreTokens(savedUser);
}
```

사용자 생성 이후 카드 지급과 환영 메시지 생성까지 하나의 트랜잭션에서 처리했다.

#### After — 개선 코드

**1. 메인 로그인 트랜잭션**

```java
@Transactional
public Result<AuthResponse> loginAsGuest(
        GuestLoginRequest request) {

    User savedUser = userRepository.save(guestUser);

    createSubEntities(savedUser);

    // 가입 후처리를 위한 비동기 이벤트 발행
    eventPublisher.publishEvent(
        new UserRegistrationEvent(
            savedUser.getId(),
            AuthProvider.GUEST,
            lang
        )
    );

    return generateAndStoreTokens(savedUser);
}
```

**2. 백그라운드 이벤트 리스너**

```java
@Async("eventTaskExecutor")
@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT
)
@Transactional(
    propagation = Propagation.REQUIRES_NEW
)
public void handleUserRegistration(
        UserRegistrationEvent event) {

    // 메인 트랜잭션 커밋 이후 별도 트랜잭션에서 실행
    assignDefaultCardItems(event.userId());

    sendGuestWelcomeMessage(
        event.userId(),
        event.language()
    );
}
```

#### 개선 효과

**① 트랜잭션 생명주기 단축**

로그인 API의 핵심 목적은 사용자 식별과 JWT 발급이다. 카드 지급과 가입 축하 우편 생성을 이벤트 리스너로 분리해 메인 로그인 트랜잭션의 작업량을 줄였다.

테스트에서는 커넥션 점유 시간이 약 600ms대에서 60~80ms대로 단축되는 결과가 관측됐다.

**② 핵심 인증과 부가 작업의 실행 분리**

가입 후처리에서 오류가 발생하더라도 메인 로그인 처리와 분리할 수 있다. 다만 부가 작업의 재시도와 누락 방지는 별도로 설계해야 한다.

**③ 비동기 I/O 처리**

`eventTaskExecutor`를 통해 부가 작업을 별도로 실행한다. 실제로 가상 스레드를 활용하려면 해당 실행기가 가상 스레드 기반으로 구성돼 있어야 한다.

> **주의:** Spring 애플리케이션 이벤트는 기본적으로 영속적인 메시지 저장소가 아니다. 서버 종료나 처리 실패 시에도 가입 보상 지급을 반드시 보장해야 한다면 재시도, 멱등성, Outbox 또는 메시지 큐 도입을 검토해야 한다.

### 작업 ③ 중복 DB 조회 제거

**목표:** 동일한 조회 쿼리의 반복 실행을 방지해 DB 왕복과 불필요한 부하 감소

#### After — 개선 코드

```java
Optional<User> userOpt =
    userRepository.findByAuthProviderAndProviderId(
        AuthProvider.GUEST,
        request.getDeviceId()
    );

boolean isNewGuest = userOpt.isEmpty();

User guestUser = userOpt.orElseGet(() -> ...);
```

#### 개선 효과

- 동일 조건의 조회 쿼리를 2회에서 1회로 감소
- 불필요한 DB 왕복 제거
- DB 쿼리 실행량 감소
- 요청량 증가 시 누적되는 불필요한 DB 부하 완화

DB 왕복을 한 번 줄였을 때의 실제 지연 시간 감소 폭은 쿼리 실행 시간과 DB 연결 환경에 따라 달라진다.

---

### 작업 ④ 소셜 로그인 외부 통신과 DB 트랜잭션 분리 및 캐싱

**목표:** Google 및 Apple 인증 과정에서 외부 통신이 발생하더라도 DB 커넥션을 불필요하게 점유하지 않도록 개선

#### Before — 문제 코드

```java
@Transactional
public Result<AuthResponse> loginWithApple(
        AppleLoginRequest request) {

    // 외부 HTTP 통신이 진행되는 동안
    // 트랜잭션이 유지될 수 있음
    Result<AppleUserInfo> validateResult =
        validateAppleIdentityToken(
            request.getIdentityToken()
        );

    ...
}
```

기존 구조에서는 외부 토큰 검증과 DB 작업이 하나의 트랜잭션 경계에 포함돼 있었다.

외부 인증 서버 응답이 느려지면 DB 커넥션을 사용하지 않는 시간에도 커넥션 점유가 이어질 수 있었다.

#### After — 개선 코드

**1. 외부 인증 검증**

```java
// 외부 통신과 토큰 검증을 트랜잭션 밖에서 수행
public Result<AuthResponse> loginWithApple(
        AppleLoginRequest request) {

    Result<AppleUserInfo> validateResult =
        validateAppleIdentityToken(
            request.getIdentityToken()
        );

    ...

    return processAppleUserLogin(
        validateResult.getData(),
        request.getFcmToken()
    );
}
```

**2. DB 작업에만 트랜잭션 적용**

```java
@Transactional
public Result<AuthResponse> processAppleUserLogin(
        ...) {

    // 사용자 조회, 생성 및 DB 관련 작업
    ...
}
```

#### 개선 효과

**① 외부 통신과 DB 커넥션 점유 분리**

Apple 토큰 검증 등 외부 통신이 진행되는 동안 불필요하게 DB 커넥션을 점유하지 않도록 트랜잭션 경계를 조정했다.

**② 외부 인증 지연의 영향 완화**

인증 서버의 응답 지연이 DB 커넥션 풀 고갈로 직접 이어질 가능성을 낮췄다.

**③ 인증 검증 비용 최적화**

Google Verifier를 싱글톤으로 재사용하고 Apple 공개키를 메모리에 캐싱해, 캐시 적중 시 반복적인 초기화 또는 공개키 조회에 필요한 외부 네트워크 비용을 줄이도록 개선했다.

## 5. 2차 테스트에서 발견한 남은 문제

리팩토링 이후 일부 핵심 지표는 개선됐지만, P50과 P95 응답 시간은 오히려 증가했다.

### 5.1. 응답 시간 비교

| 지표 | 1차 테스트 | 2차 테스트 | 변화 |
|---|---:|---:|---|
| P50 | 100ms | 130ms | 30ms 증가 |
| P95 | 180ms | 240ms | 60ms 증가 |
| P99 | 550ms | 290ms | 260ms 감소 |

### 5.2. 결과 해석

**P99는 개선됐지만 P50과 P95는 악화됐다.**

1차 테스트에서는 요청이 처리되는 동안 일부 트랜잭션이 커넥션을 오랫동안 점유했다. 이로 인해 특정 요청이 커넥션을 획득하지 못하고 오랫동안 대기하는 현상이 발생했다.

2차 테스트에서는 메인 로그인 트랜잭션의 작업량과 SQL 쿼리 수를 줄였다. 그 결과 극단적인 지연을 경험하는 요청의 응답 시간이 감소하면서 P99가 550ms에서 290ms로 단축됐다.

반면, 2차 테스트에서는 비동기로 분리한 카드 지급과 환영 메시지 생성 작업도 여전히 DB 커넥션을 사용한다. 이 부가 작업이 로그인 요청과 동일한 커넥션 풀을 사용한다면 피크 타임에 경쟁이 발생할 수 있다.

실제로 테스트에서는 Pending이 최대 47개까지 발생한 것으로 관측됐다.

따라서 현재 결과는 다음과 같이 해석할 수 있다.

- **P99:** 극단적인 지연이 감소했다.
- **P50:** 일반적인 요청 구간의 응답 시간이 증가했다.
- **P95:** 상위 지연 구간의 응답 시간이 증가했다.
- **커넥션 풀:** 메인 트랜잭션의 부담은 줄었지만, 비동기 작업과의 커넥션 경쟁은 남아 있을 수 있다.

즉, **극단적인 지연은 완화됐지만, 전체 요청의 응답 시간이 모든 구간에서 개선된 것은 아니다.**

이 결과만으로 비동기 이벤트 분리가 P50·P95 상승의 직접적인 원인이라고 단정할 수는 없다. 부하 발생 패턴, 커넥션 대기 시간, 비동기 작업 실행량을 함께 비교해 원인을 확인해야 한다.

## 6. 커넥션 풀 크기를 늘리는 것이 정답일까?

현재 테스트 환경에서는 HikariCP 커넥션 풀 크기 20개를 사용했다.

단순히 커넥션 풀 크기를 늘리면 일부 대기 현상을 완화할 수 있다. 하지만 커넥션 수가 늘어난다고 항상 성능이 좋아지는 것은 아니다.

DB가 처리할 수 있는 동시 작업량보다 더 많은 커넥션을 열면 DB 서버의 메모리와 CPU 부담이 증가하고, 오히려 처리 성능이 떨어질 수 있다.

따라서 현재 환경에서 우선 확인할 항목은 다음과 같다.

1. 비동기 작업과 로그인 요청이 동일한 커넥션 풀을 공유하는지 확인한다.
2. 비동기 작업이 집중될 때 HikariCP Active, Idle, Pending 지표가 어떻게 변하는지 확인한다.
3. 메인 로그인 트랜잭션과 백그라운드 작업의 커넥션 점유 시간을 비교한다.
4. DB 서버의 실제 처리 용량을 고려한 뒤 커넥션 풀 크기를 조정한다.

**커넥션 풀의 크기를 늘리기 전에 커넥션을 오래 점유하는 원인을 제거하는 것이 우선이다.**

## 7. 추가 개선 방향

### 7.1. 비동기 작업의 실행량 제어

가입 요청이 단시간에 집중되면 비동기 작업 역시 동시에 실행되면서 DB 커넥션 경쟁을 일으킬 수 있다.

따라서 비동기 작업에 동시 실행 수 제한이나 처리량 제어를 적용해, 메인 로그인 요청에 미치는 영향을 줄이는 방법을 검토할 수 있다.

### 7.2. 메시지 큐 도입

로그인 요청이 대량으로 몰리는 환경이라면 가입 후처리 이벤트를 메시지 큐에 넣고, 소비자가 일정한 속도로 처리하도록 구성할 수 있다.

예를 들어 다음과 같은 구조다.

```text
[Guest Login API]
        |
        v
[User 생성 및 JWT 발급]
        |
        v
[가입 이벤트 발행]
        |
        v
[Message Queue]
        |
        v
[Background Consumer]
        |
        +-- 기본 카드 아이템 지급
        |
        +-- 가입 축하 우편 생성
```

이 구조의 목적은 핵심 로그인 요청과 부가적인 DB 작업의 실행 시점을 분리하고, 부하가 집중되는 상황에서 후처리 작업의 처리량을 제어하는 것이다.

메시지 큐를 도입하면 재시도와 장애 복구를 더 체계적으로 구성할 수 있지만, 이벤트 중복 소비에 대비한 멱등성 처리와 이벤트 발행·DB 커밋 간의 정합성도 함께 설계해야 한다.

### 7.3. 후속 부하 테스트

다음 테스트에서는 응답 시간만 확인하기보다, 메인 요청과 비동기 작업이 커넥션 풀을 어떻게 사용하는지 함께 비교할 필요가 있다.

| 확인 항목 | 검증 목적 |
|---|---|
| P50 / P95 / P99 | 일반적인 지연과 극단적인 지연을 구분 |
| HikariCP Active / Idle / Pending | 커넥션 풀 포화 및 대기 여부 확인 |
| 메인 트랜잭션 점유 시간 | 로그인 API의 DB 점유 시간 측정 |
| 비동기 작업 실행량과 처리 시간 | 백그라운드 작업으로 인한 경합 확인 |
| SQL 실행 횟수 및 실행 시간 | 실제 DB 병목과 불필요한 쿼리 확인 |
| 오류율 | 성능 개선과 기능적 안정성을 함께 검증 |

## 8. 최종 정리

이번 작업의 핵심은 단순히 SQL 쿼리 몇 개를 줄이는 데 있지 않다.

**DB 커넥션을 점유하는 시간을 줄이고, 로그인 핵심 로직과 부가 작업의 경계를 명확하게 나누는 것**이 주요 목표였다.

이번 리팩토링에서는 다음과 같은 개선을 진행했다.

- 닉네임 생성 방식을 개선해 동시 요청 시 중복 발생 가능성을 낮췄다.
- 가입 후처리를 비동기 이벤트로 분리해 메인 트랜잭션의 작업량을 줄였다.
- 동일한 DB 조회 결과를 재사용해 중복 쿼리를 제거했다.
- 소셜 로그인에서 외부 인증 통신과 DB 트랜잭션을 분리했다.
- 인증 검증 객체의 재사용과 공개키 캐싱을 적용했다.

그 결과 요청 실패 건수, 총 SQL 쿼리 수, SQL 최대 실행 시간, P99 응답 시간에서 개선이 관측됐다.

다만 P50과 P95 응답 시간은 증가했고, 비동기 작업을 수행하는 과정에서도 DB 커넥션 경쟁이 발생할 가능성이 남아 있다. 따라서 현재 단계에서 성능 개선이 완전히 끝났다고 판단하기보다는, **극단적인 지연을 줄이는 데는 성과가 있었지만 일반 요청의 응답 시간과 커넥션 사용 효율을 추가로 개선해야 하는 상태**로 보는 것이 타당하다.

다음 단계에서는 비동기 작업의 DB 점유 시간과 실행량을 분석하고, 필요하다면 실행량 제어 또는 메시지 큐 도입을 통해 로그인 요청과 가입 후처리의 부하를 더욱 효과적으로 분리할 계획이다.
